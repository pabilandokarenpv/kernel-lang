Add a module system + package manifest skeleton (completes Option C)

- ast.rs: new Item::Import(String) -- `import foo` / `import utils.math`,
  a dotted module path. Defensive unreachable!() arms added to the two
  exhaustive Item matches this broke (interpreter.rs's load(),
  lambda_lift.rs's known_names collection) since Import should never
  survive past modules.rs.
- parser.rs: parses `import` + a dotted path in parse_item() (reuses the
  existing Dot token).
- modules.rs (new): the actual module system. Resolves every Item::Import
  by reading the target file RELATIVE TO THE IMPORTING FILE's own
  directory, recursively resolving its imports too, and splicing its
  top-level items directly into the program -- unqualified, no pub/
  private visibility, exactly as if pasted in. Cycle/duplicate-import
  safe via a canonicalized-path visited-set (tested: a real circular
  import a<->b resolves fine, and a diamond import -- main importing
  both utils and geometry where utils ALSO imports geometry -- correctly
  includes geometry only once). Runs as the very FIRST pass (before
  monomorphize/lambda_lift), so generics/closures defined in an imported
  file are handled identically to ones in the entry file. Also adds a
  real duplicate-top-level-name check across the merged program (a name
  collision between two files, or a file and the entry point, is a loud
  error -- checker.rs/interpreter.rs/codegen_c.rs all build their name
  tables via plain HashMap::insert, which would otherwise silently let
  a later definition overwrite an earlier one).
- lsp.rs: analyze() now takes the document's path (derived from its URI)
  and resolves imports too, so editor diagnostics stay consistent with
  what `kernel run`/`kernel build` would actually do for a program using
  `import` -- verified against a real stdio session opening
  examples/modules/main.kn (zero diagnostics, as expected for a valid
  program).
- manifest.rs (new) + `kernel init [name]` subcommand: a package-manager
  SKELETON, explicitly named as exactly that -- a minimal `kernel.toml`
  (flat key="value" lines, not full TOML, hand-parsed, no dependency)
  naming a project and its entry file. `kernel run`/`kernel build`/
  `kernel tokens`/`kernel trace` now resolve their default path through
  it when no explicit path is given (falls back to the original
  examples/hello.kn default when no manifest exists -- verified
  unchanged). No registry, no remote dependencies, no version
  resolution -- it only establishes the manifest file + the commands
  that read it, which a real future package manager would build on now
  that there's a module system for a project to actually span multiple
  files with.
- examples/modules/{main,utils,geometry}.kn: a real 3-file program
  (diamond import) verified end to end -- interpreter, C codegen, AND a
  real QEMU boot with screendump (pixel-exact 5|0|0).
- Full existing example suite + LSP test re-run: zero regressions,
  negative tests still rejected.

This completes Option C (developer experience): LSP, basic stdlib
(len/file I/O), and now a module system + package manifest skeleton.
Per the agreed A -> C -> B order, Option B (LLVM backend) is next.
